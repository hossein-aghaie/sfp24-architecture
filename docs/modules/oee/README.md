# OEE — راهنمای شروع نویسندهٔ ماژول

این ماژول برای سنجش اثربخشی تجهیزات است: چه بخشی از زمان موردنظر قابل استفاده بوده، تولید با چه عملکردی انجام شده و چه بخشی از خروجی سالم بوده است. قرار نیست صرفاً چند تگ روی یک داشبورد نشان داده شود.

**وضعیت:** نامزد طراحی؛ موتور عمومی OEE و قرارداد اتصال مستقل آن هنوز ساخته و تأیید نشده‌اند. این صفحه مسیر ادامهٔ کار است، نه مجوز شروع کدنویسی یا ادعای API آماده. [وضعیت برنامه](../../STATUS.fa.md).

| ترتیب | سند | پاسخ کدام سؤال؟ |

| ۲ | [معماری](../../core/ARCHITECTURE.fa.md) | هسته، دریافت داده، دیتابیس شرکت و ماژول چه مسئولیتی دارند؟ |

| ۴ | [داده و پارامتر](../../core/DATA-AND-PARAMETERS.fa.md) | منبع، تگ و پارامتر چه تفاوتی دارند و معنای زمان/مقدار چیست؟ |

آرشیو همهٔ گفتگوها و اسناد آموزش پیش‌نیاز این مسیر نیست. اگر پرسشی از این اسناد پاسخ ندارد، آن را نامعلوم ثبت کنید و [درخواست](../../governance/CHANGE-WORKFLOW.md) بدهید.

## دادهٔ موردنیاز و چیزی که هنوز مشخص نیست

این جدول فهرست نیازهای طراحی است؛ نام سرویس یا تضمین موجودبودن داده نیست.

| نیاز OEE | از کجا باید بررسی شود؟ | هنوز چه باید روشن شود؟ |
|---|---|---|
| تجهیز و محدودهٔ محاسبه | تعاریف مشترک تجهیز و دسترسی هسته | قرارداد خواندن، شناسه‌ها و محدودهٔ مجاز مصرف‌کننده |
| مدت موردنظر برای تولید | تقویم/برنامهٔ کاری یا تعریف معتبر بازه | مرجع زمان مبنا و قواعد استراحت/توقف برنامه‌ریزی‌شده؛ الزام به خرید ماژول برنامه‌ریزی تصمیم نشده |
| زمان کار و توقف تجهیز | پارامتر/رویداد معتبر یا ثبت تأییدشده | آیا سیگنال برای تشخیص حالت کافی است؟ دادهٔ ناقص چه اثری دارد؟ |
| تعداد و معنای شمارش | پارامتر با نوع، واحد و پوشش زمانی | تعداد همان دقیقه است یا تجمعی؟ مرز بازه و دادهٔ دیررس چیست؟ |
| تعداد سالم و نامنطبق | ثبت معتبر کیفیت/تولید یا ورودی تعیین‌شده | منبع معتبر کدام است و بدون ماژول کیفیت چه مسیری داریم؟ |
| سیکل مرجع | اطلاعات معتبر تجهیز/قطعه/OP | نگهداری مقدار و نسخه، تغییر قطعه و چندعملیاتی‌بودن |

وابستگی اجباری به تولید، کیفیت یا برنامه‌ریزی هنوز از این جدول نتیجه نمی‌شود. برای هر ورودی، منبع حداقلی و رفتار نبودِ ماژول باید در طراحی OEE مشخص و تأیید شود.

## مسیر داده تا نمایش

مسیر مفهومی دریافت خودکار: **دستگاه ← هاب و تگ ← پارامتر مناسب ← محاسبهٔ OEE ← گزارش یا ابزار نمایش مجاز**. ورودی دستی هم می‌تواند از ثبت معتبر عملیاتی بیاید و نیاز به تگ مصنوعی ندارد. [تعریف اصلی مسیر داده](../../core/DATA-AND-PARAMETERS.fa.md).

مصرف شمارش در ماژول تولید شاهد یک مصرف‌کنندهٔ موجود است؛ API عمومی آماده برای OEE فرض نمی‌شود. نویسندهٔ OEE باید نیاز خواندن پارامترها در یک بازه و نتیجهٔ مجاز را مشخص کند؛ هسته باید اتصال قابل پشتیبانی یا کمبود آن را پاسخ دهد. [راهنمای مصرف موجود تولید](../../operations/guides/PRODUCTION-DATA-SOURCES.md).

خروجی موردنیاز، نتیجهٔ قابل توضیح با تجهیز/دامنه، بازه، ورودی‌های استفاده‌شده، روش و نسخهٔ محاسبه و کمبود داده است؛ نه فقط یک درصد. شکل دقیق ذخیره، API خروجی و اتصال به میز/داشبورد هنوز باید تعیین شود. Widget نباید محل پنهان‌کردن منطق رسمی محاسبه باشد. [پیش‌نویس رابط ماژول](../../contracts/UI-CONTRIBUTIONS-DRAFT.md).

## خطاهایی که نباید وارد طراحی شوند

- قطع ارتباط دستگاه را خاموشی یا توقف فیزیکی فرض نکنید؛ نبود داده صفر نیست.
- شمارش دستگاه، تعداد سالم، شخص انجام‌دهنده و OP را به‌تنهایی ثابت نمی‌کند.
- حضور فرد، بازهٔ گزارش و روشن‌بودن ماشین، زمان مبنای یکسان نیستند.
- میانگین سادهٔ OEE دستگاه‌ها را «OEE سالن» ننامید؛ دامنه و روش تجمیع باید تعریف شوند.
- نقش شغلی یا نمایش یک ابزار جای مجوز سمت سرور را نمی‌گیرد؛ جداسازی شرکت‌ها باید حفظ شود.

## قدم بعدی واقعی این ماژول

ابتدا یک سناریوی قابل آزمون انتخاب شود و ورودی‌های جدول بالا برای همان سناریو تعیین شوند. خروجی این مرحله «طراحی قابل بررسی و کمبودهای اتصال» است؛ هنوز نه موتور OEE و نه قول انطباق با استاندارد خاص. انتخاب روش محاسبه و منابع استاندارد در تحقیق خود OEE با نسخه و منبع ثبت می‌شود.

هر کمبود هسته یا ماژول دیگر با [قالب درخواست](../../governance/CHANGE-WORKFLOW.md) و ثبت در [فهرست درخواست‌ها](../../governance/REQUESTS.md) پیگیری شود؛ [REQ-oee-0001](requests/REQ-oee-0001-data-and-output.md) کمبود واقعیِ مستندات اتصال پارامتر و خروجی را ثبت کرده و هنوز تصمیم فنی ندارد. برای قرارداد نامعلوم API یا schema اختراع نکنید.

[قواعد ثبت و حفظ سوابق](../../governance/DOCUMENTATION-POLICY.md).
