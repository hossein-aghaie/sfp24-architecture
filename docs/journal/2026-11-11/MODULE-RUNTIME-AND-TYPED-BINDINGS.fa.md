# اتاق فکر — مدل اجرای ماژول‌ها و اتصال نوع‌دار داده‌ها (Element / Input / Output)

**تاریخ گفتگو و ثبت:** ۲۰۲۶-۱۱-۱۱  
**منشأ:** گفت‌وگوی صاحب محصول با دستیار هنگام انتظار برای گزارش Codex دربارهٔ P4-A  
**نوع مدرک:** متن واقعی پیام صاحب محصول + خلاصه و تحلیل دستیار، با تفکیک صریح؛ نه رونوشت کامل همهٔ پیام‌های گفتگو  
**وضعیت:** Open / Thinking Aloud — نه ADR مصوب، نه قرارداد اجرایی، نه دستور تغییر کد  
**اثر بر کار جاری:** مأموریت P4-A همان بررسی فقط‌خواندنی است؛ این یادداشت محدوده یا مجوز آن را تغییر نمی‌دهد.

## ۱. متن واقعی پیام صاحب محصول

> خیلی خوب، تا وقتی که جواب کدکس بیاد، به نظرم من توی این وسط‌ها بیاییم در مورد این که ماژول ما یک میکروسرویس جدا با تکنولوژی بک و فرانت احتمالاً جدا آیا می‌تونن باشن، نمی‌تونن باشن یا نه فرانت باید مشترک باشه با ما و بک‌اند می‌تونه زبان‌های مختلف داشته باشه، ساختار مونولیتیک یا میکروسرویس اگر باشه باید چی کار بکنیم، و یا در مورد این که این elementها داستان رو باید جمع کنیم به یه جمع‌بندی برسیم، کار زیاد داریم. element هم خیلی مهمه، مثلاً ورودی‌هایی که از حس می‌گیره، مثلاً این‌جوری باشه که input مثلاً input dot person dot فلان مثلاً یا machine dot parameter و همه چیزای باید تعریف کنیم که بعداً این همه رو به هم اتصال بدیم. در مورد اینا هم باید بشینیم فکر کنیم. من تا وقتی که کدکس کارش رو تموم کنه و گزارشش رو بهت بدم، پیشنهاد می‌کنم یه فکری هم در مورد اینا بکنیم که شاید نیاز باشه وسط این کارا انجام بدی. البته اینم نمی‌خوام جوری باشه که مسیرتو عوض کنی، فقط خواستم یه suggestionی داشته باشم.

**یادداشت منشأ:** متن بالا نقل مستقیم پیام در همین گفتگو، با نگارش گفتاری موجود است. بخش‌های بعدی برداشت و پیشنهاد دستیارند، نه نقل‌قول یا تصمیم صاحب محصول. صاحب محصول در پیام بعدی درخواست کرد این بحث برای فراموش‌نشدن در مخزن اسناد ثبت شود.

## ۲. مسئله‌های بازِ مطرح‌شده

### ۲.۱. مدل اجرا و فناوری ماژول

پرسش اصلی: آیا همهٔ ماژول‌ها باید در فرایند و فناوری مشترک Host اجرا شوند، یا می‌توانند سرویس مستقلی با Backend و حتی Frontend متفاوت داشته باشند؟

گزینه‌های قابل بررسی، **نه گزینه‌های تصویب‌شده**:

- **Trusted Modular Monolith:** ماژول داخل Build و Runtime مشترک؛ در وضعیت فعلی TypeScript برای Backend و Vue برای UI طبیعی‌تر است.
- **Out-of-process Service:** Backend مستقل با زبان متفاوت (مثلاً Python یا .NET)، متصل از طریق API/Port/Event نسخه‌دار و با احراز هویت سرویس و Tenant Context معتبر.
- **Microfrontend / رابط مستقل:** UI با فناوری متفاوت، ولی برای حضور در میزهای Host نیازمند Adapter، قرارداد Mount، کنترل دسترسی، Context و مدیریت خطا/نسخه است؛ پشتیبانی عمومی از آن اکنون اثبات نشده است.
- **مدل ترکیبی:** UI در Host و پردازش تخصصی در سرویس مستقل؛ یا ترکیب انتخابی این الگوها.

**برداشت اولیهٔ دستیار:** Modular Monolith مورد اعتماد می‌تواند مسیر پیش‌فرض کوتاه‌مدت باشد، در حالی که قراردادها مانع جداسازی انتخابی آینده نشوند. این برداشت به معنی الزام ابدی به Vue/TypeScript یا تصمیم به Microservice برای هر ماژول نیست.

### ۲.۲. Element و اتصال ورودی/خروجی‌ها

پرسش اصلی: برای اتصال سنسورها، پارامترهای ماشین، ویژگی‌های شخص، خروجی محاسبات، عملیات ماژول‌ها و Widgetها به یکدیگر چه هویت و قرارداد مشترکی لازم است؟ نمونه‌های گفتاری «input dot person dot ...» و «machine dot parameter» **ایدهٔ نحو آدرس‌دهی** هستند، نه نام یا API تصویب‌شده.

**برداشت اولیهٔ دستیار:** پیش از تعریف یک Element همه‌منظوره، سه مسئولیت باید از هم تفکیک شوند:

1. **Identity / Definition:** شیء یا قابلیت چیست، مالک آن کدام حوزه است، نوع، شناسه و نسخه‌اش چیست؟
2. **Reference / Binding:** چگونه با ارجاع پایدار و نوع‌دار به آن اشاره می‌کنیم و منبع را به مصرف‌کننده یا Context متصل می‌کنیم؟
3. **Consumption / Execution:** خواندن، ثبت، محاسبه، نمایش یا اجرای فرمان با چه قرارداد و Permission و Scope انجام می‌شود؟

مفهوم‌های موجود **یکسان نیستند**: Source/Tag دریافت داده، Parameter تعریف معنایی و نسخه‌دار، DomainRef ارجاع به رکورد دامنه، Port مسیر Query/Action، Event اعلام رخداد و UI Contribution جایگاه نمایش را پوشش می‌دهند. یکسان‌کردن آن‌ها زیر نام Element بدون بررسی، خطر از دست‌رفتن معنا و مالکیت دارد.

در طراحی آینده باید نوع و واحد، ساختار زمانی، کیفیت و منشأ داده، نسخهٔ تعریف و تبدیل، Tenant/Scope، مالک داده، وضعیت نبود داده، سیاست مجوز، رفتار هنگام Disable و تفاوت Query با Command و Event روشن شوند. نام خوانا نباید جای شناسهٔ پایدار را بگیرد. **این‌ها موضوع بررسی‌اند، نه ادعای نبود یا الزام به بازطراحی همهٔ قراردادهای موجود.**

## ۴. پرسش‌های باز برای نوبت تصمیم‌گیری

1. حداقل قرارداد ثابت میان Host و ماژول‌های داخل Runtime یا سرویس مستقل چیست؟ مالکیت داده، امنیت Tenant، نسخه، استقرار، خرابی و بازیابی چگونه تعیین می‌شوند؟
2. Frontend متفاوت دقیقاً چه نیازی را حل می‌کند و آیا Adapter/Microfrontend ارزش هزینهٔ امنیتی و عملیاتی را دارد؟
3. آیا «Element» نام یک موجودیت مشترک است یا خانواده‌ای از Reference، Binding، Port، Event و UI Contribution؟ کدام مفهوم از قبل مالک معتبر دارد؟
4. نحو خوانای آدرس‌دهی چگونه به شناسهٔ پایدار، نوع، واحد، زمان، نسخه و Scope متصل می‌شود؟
5. برای اتصال چند ماژول، کدام سناریوی واقعی نخستین مصرف‌کنندهٔ این قرارداد خواهد بود و چه آزمونی استقلال را اثبات می‌کند؟
6. کدام تصمیم‌ها پیش از P4-B ضروری‌اند و کدام را می‌توان تا ظهور نیاز واقعی باز گذاشت؟
