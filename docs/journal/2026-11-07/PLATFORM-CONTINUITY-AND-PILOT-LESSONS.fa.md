## ۱. چرا این نوشته وجود دارد؟

مالک محصول نگران است که با ورود و خروج از سشن‌ها، گم‌شدن پیام‌ها، و رفت‌وبرگشت گزارش‌های Codex، تحلیل بنیادی اخیر فراموش شود و پروژه دوباره به «تونل UI/UX» یا توسعهٔ یک ماژول خاص محدود گردد. این سند لنگر استمرار است: سشن و ایجنت تازه باید **ابتدا وضعیت واقعی جدید را بررسی کند**، سپس این تحلیل، اصول ثابت و مسائل باز را در تصمیم‌گیری حفظ کند؛ نه آنکه متن را بدون راستی‌آزمایی به واقعیت دائمی تبدیل کند.

## ۲. هدف محصول که نباید زیر سؤالِ تغییرات ظاهری گم شود

SFP24 بناست بستر ماژولار و قابل تنظیم برای دامنهٔ وسیعی از شرکت‌ها باشد: از کارگاه کوچک با یک نفر و چند مسئولیت و ثبت دستی ساده، تا سازمان بزرگ چندواحدی و چندسایتی با ماژول‌های متفاوت، تعاملات بین‌ماژولی، گردش کار و تأییدهای چندمرحله‌ای، دریافت داده از دستگاه/هاب و ارائهٔ اطلاعات متناسب با نقش و زمینهٔ کار. این دو سر طیف «دو محصول جدا» یا «دو مرحلهٔ اجباری رشد هر مشتری» نیستند. میز کار، داشبورد، پروفایل، کارتابل و نمای سه‌بعدی **روش‌های نمایش و تعامل** هستند، نه خودِ موتور عملیاتی ماژول.

باید بتوان بدون بازنویسی وسیع هسته، ماژول‌های جدید و نسخه‌های متفاوت رفتار ماژول را به قراردادهای مشترک متصل کرد. این هدف **هنوز در همهٔ ابعاد اثبات نشده**؛ نباید با موفقیت دو ماژول اولیه یکسان فرض شود.

## ۳. آسیب‌شناسی: چه اتفاقی افتاد؟

### ۳.۱. ادغام محیط ایزوله، علت اصلیِ اثبات‌شده نیست

سه رویداد متمایز بودند: (الف) توسعهٔ شاخهٔ پایلوت در Git Worktree جدا، (ب) آزمون با دادهٔ Fixture در MariaDB ایزوله، (ج) فعال‌کردن همان کد در پوشهٔ روزمره و ساخت دو شرکت نمایشی ماندگار. انتقال، به‌خودی‌خود، دو UI مستقل را «به هم نچسبانده» است. شواهد کد در بررسی پیشین نشان می‌دادند Studio Preview و Runtime عملیاتی از دو مسیر مختلف استفاده می‌کنند. این اختلاف قبل از انتقال قابل وقوع بوده است. با این حال، دربارهٔ **یکسان بودن دقیق اسکرین‌شات‌های محیط ایزوله و محیط روزمره** بدون آزمون تطبیقی نباید ادعای قطعی کرد؛ مجوز، داده و تنظیم میز ممکن است تفاوت نمایش ایجاد کنند.

برگرداندن پروژه به محیط جدا مشکل اصلی طراحی را حل نمی‌کرد؛ فقط ممکن بود کشف آن را عقب بیندازد. محیط ایزوله برای Migration، سازگاری و تست مخرب همچنان ابزار مفیدی است، اما مشاهدهٔ محصول توسط مالک باید از محیط روزمرهٔ قابل ورود فراهم باشد.

### ۳.۲. چهار عاملِ محتملِ اصلی

۱. **ادامهٔ مسیر نیمه‌تمام Desk Builder قدیمی:** میزساز زمانی آغاز شد که دامنهٔ ماژول‌ها، Task، Approval، تعاملات و متادیتای بین‌ماژولی به اندازهٔ امروز روشن نبود. شناخت جدید در اسناد ثبت شد، اما تمام پیش‌فرض‌های پیاده‌سازی قدیمی بازبینی نشده بودند.

۲. **افزودن قابلیت‌های جدید به Host موجود:** Codex برای حفظ سازگاری، Production و Maintenance و گردش کار را به ساختار فعلی وصل کرد. پیشرفت عملکردی قابل مشاهده بود، ولی یکپارچگی UX و نقش موتور نمایش مشترک به همان اندازه اثبات نشد.

۳. **معیار پذیرش ناکافی:** تست‌ها عمدتاً درستی Domain، ثبت داده، مجوز، جداسازی Tenant، Revision و Approval را اندازه گرفتند؛ «Studio و Runtime برای یک DeskDefinition یک تجربهٔ منطبق و قابل فهم تحویل می‌دهند» و «اپراتور بدون راهنما می‌تواند کار کند» به اندازهٔ کافی موضوع پذیرش نبودند. عکس گرفتن در Chrome به‌تنهایی معادل پذیرش انسانی نیست.

۴. **اختلاط پیشنهاد و قرارداد تثبیت‌شده:** در اسناد، موضوعاتی مانند مفهوم نهایی Workspace/Room، UI Contribution، Task مشترک و SDK مستقل هنوز باز یا Proposed بودند. اجرای پایلوت ناگزیر انتخاب‌هایی کرد که باید برچسب «موقت»، «فقط برای پایلوت»، «مصوب» یا «اثبات‌نشده» داشته باشند؛ نباید تصمیم موقت به قانون کل SFP24 تبدیل شود.

اختلال و از دست رفتن بخشی از تاریخچهٔ گفتگو انتقال دانش را دشوار کرده، ولی علت فنیِ اثبات‌شدهٔ کیفیت پایین UX نیست.

### ۳.۳. واقعیت کد که در بررسی پیشین شناسایی شد

- `DeskStudioPreview.vue` از `DeskExperiencePreview.vue` برای تجربهٔ شبیه‌سازی‌شده استفاده می‌کرد.
- `AssignedDesk.vue` از `DeskRuntime.vue` برای عملیات واقعی استفاده می‌کرد.
- `workspaces.ts` و Policyهای پیش‌فرض، بر اساس ترکیب Workspace و Permission برخی صفحات را به کاربر نشان می‌دادند؛ `master.read` امکان دسترسی به برخی صفحات مدیریتی‌مانند را ایجاد می‌کرد، بدون اینکه الزاماً `master.manage` داده شده باشد.
- `seed-pilot-companies.ts` به حساب اپراتور Mihan اختیارات عملیاتی متنوعی می‌داد و Desk را با مجموعه Widget ثابت می‌ساخت.
- بخشی از اتصال UI Contributionها به Host هنوز ثابت بود؛ رجیستری فنی به‌تنهایی افزودن هر Module UI جدید را بدون تغییر Host اثبات نمی‌کرد.

**این‌ها شواهد مبنای آن تاریخ‌اند، نه ادعای وضعیت پس از مأموریت جاری Codex.** هر سشن بعدی باید Diff و Runtime جدید را بررسی کند.

## ۴. آیا UI نامناسب به معنی Backend معیوب است؟

خیر. تست‌های گزارش‌شده برای ثبت تولید، درخواست تعمیر، ارجاع، دو تأیید مستقل، مجوز و جداسازی Tenant شواهد مثبت محدودی از درستی عملکرد همان سناریوها هستند. از زشت بودن UI نمی‌توان شکست بک‌اند را نتیجه گرفت. از طرف دیگر، موفقیت تست‌هایی که همان ایجنت نوشته و اجرا کرده، به‌تنهایی استقلال و توسعه‌پذیری قراردادهای بک‌اند را ثابت نمی‌کند. ریسک باقی‌مانده: اتصال‌های ثابت به Host، تکرار منطق، مالکیت Domain، Task/Event/Approval مشترک، Lifecycle ماژول، سازگاری نسخه‌ها و وابستگی به چند ماژول اولیه. **کیفیت عملکرد موجود و کیفیت معماری توسعه‌پذیر دو ارزیابی مستقل‌اند.**

## ۵. آیا میزکار نیمه‌تمام باید دور ریخته شود؟

نه. Desk Builder قدیمی دارایی و تجربهٔ پروژه است و سازگاری مدل ذخیره، شناسه‌ها و انتساب‌ها باید حفظ شود؛ اما ادامهٔ همان موتورِ Preview بدون اصلاح فرضیات آن، الزام معماری نیست. **حفظ داده و قرارداد با حفظ عینِ ساختار UI قدیمی تفاوت دارد.**

مدل هدف برای بررسی: یک «تعریف معتبر تجربهٔ کاربر» شامل Desk Definition، Layout، Contribution و Context؛ Studio Preview و Runtime از همان قواعد چیدمان/ترکیب استفاده کنند ولی Preview از دادهٔ نمونهٔ غیراثرگذار و Runtime از Query/Action واقعی و مجاز بهره ببرد. این الگو **جهت پیشنهادی** است و صحت پیاده‌سازی آن باید در تحویل فعلی اثبات شود.

## ۶. مرزهای طراحی تجربه که از مسیر اصلی محافظت می‌کنند

- SFP24 «نرم‌افزار میزکار» نیست؛ **بستری ماژولار** است و Desk تنها یک شیوهٔ نمایش است.
- ماژول ممکن است Form، Full Page، Gantt، Profile Section، Dashboard، Inbox، Notification یا نمای سه‌بعدی تخصصی نیاز داشته باشد. همه‌چیز را به کارت کوچک Desk محدود نکنیم.
- UI تعیین‌کنندهٔ Permission نیست؛ Backend در زمان Action باید Entitlement/Readiness، Permission، Scope، Domain Policy و Revision را کنترل کند.
- Tag/Parameter با Domain Record و Workflow یکسان نیست؛ یک وضعیت خام دستگاه به‌خودی‌خود نتیجهٔ عملیاتی معتبر ایجاد نمی‌کند.
- چند مسئولیت برای یک نفر نباید به چند حساب مصنوعی منجر شود؛ تأیید مستقل در موارد لازم همچنان استقلال اشخاص را مطالبه می‌کند.
- پیکربندی نمایش/میز نباید کد دلخواه مشتری، SQL آزاد، یا موتور امنیتی موازی بسازد.
- داشتن قابلیت آماده در Backend به معنی تجربهٔ قابل استفاده برای کاربر نیست.

## ۷. برنامهٔ پس از تحویل مأموریت فعلی Codex

### گام ۱ — تثبیت تحویل Codex، بدون مداخلهٔ موازی

صاحب محصول اعلام کرده Codex مأموریت اصلاح رابطهٔ Workspace/Desk، Studio و Runtime، ناوبری، فرم‌های عملیاتی و مسیرهای UI Contribution را تمام کرده است. تا دریافت و بررسی گزارش نهایی هیچ فرمان تغییر متعارض، Refactor موازی یا تغییر مستقل در مخزن‌ها انجام نشود. تحویل باید شامل SHA دقیق، Diff، تست‌های واقعاً اجراشده، تصویر/ویدئوی **واقعی** همان نسخه، محیط اجرا و محدودیت‌های مستند باشد.

### گام ۲ — پذیرش دوگانه، جدا از هم

**درستی فنی/امنیتی:** Production/Maintenance/Task/Approval/Permission/Tenant/Migration/Restart، با شواهد و نسخه.  
**پذیرش انسانی UX:** مالک با همان `Start-All` و کاربران واقعی نمایشی، مسیرهای Mihan و Demo Factory را شخصاً انجام دهد. پیش‌نمایش Studio برای *همان DeskDefinition* با Runtime بررسی شود. فقط اسکرین‌شات یا PASS خودکار کافی نیست.

اگر امنیت درست اما UX ضعیف است، UX باز بماند؛ اگر UI بهتر شده ولی اتصال ماژول‌ها Host-coupled است، مسئلهٔ معماری باز بماند.

### گام ۳ — بازبینی مستقل معماری، پیش از گسترش بعدی

سشن یا ایجنت مستقل از اسناد مرجع شروع کند و کد اجراشده را بررسی کند؛ نه از فرض صحت پاسخ ایجنت قبلی. خروجی باید به‌ازای هر ریسک: شاهد فایل/آزمون، اثر، شدت، گزینه‌های اصلاح، هزینهٔ تغییر و زمانِ لازم تصمیم ارائه کند. مسائل کلیدی Q01 تا Q11 و ارتباط Host/Core با Module/Capability و UI Contributions بررسی شوند. **خروجی یک فهرست تصمیم‌پذیر باشد، نه گزارش بلندِ فاقد اولویت.**

### گام ۴ — تثبیت مرز تصمیم‌ها و نقشهٔ وضعیت

برای هر قرارداد مشترک ثبت شود:
- واقعیتِ اجرا با SHA و آزمون؛
- تصمیم Approved همراه دامنهٔ تأیید؛
- Proposal/Experiment/Discussion که هنوز الزام اجرایی نیست؛
- مسئلهٔ Open و مسئول/مرحلهٔ تصمیم؛
- پیامد آن برای ماژول بعدی.

سند مرجع در مخزن معماری است؛ شواهد همان نسخه و گزارش QA کنار مخزن کد. از نگه‌داشتن دو نسخهٔ دستی و ناسازگار از یک قرارداد خودداری شود.

### گام ۵ — سامان‌دهی کد/مستندات در زمان مناسب

پس از معلوم شدن قراردادهای تثبیت‌شده، ساختار پوشه‌های هسته، ماژول، ذخیره‌سازی شرکت، مهاجرت، بکاپ، آزمون و مستندات اجرایی بررسی و *فقط در صورت نیاز مستند* اصلاح شود. صرف مرتب‌تر کردن نام فولدر دلیل Refactor گسترده نیست. با مأموریت جاری UX هم‌پوشانی و تغییر هم‌زمان نداشته باشد.

### گام ۶ — آزمون معماری با دامنهٔ متفاوت

برای کشف ضعف در قراردادهای مشترک، یک مصرف‌کنندهٔ متفاوت از Production/Maintenance انتخاب شود؛ برای نمونه Training/Skill Gap (Person، Qualification، Profile) یا OEE (Hub/Tag/Parameter، Event-Time، کیفیت داده). هدف نخست **اثبات سازگاری معماری** است، نه تولید هم‌زمان چند ماژول کامل. معیار انتخاب، قدرت کشف نقص است.

## ۸. سه معیار اجباری برای هر قابلیت در ادامه

۱. **درستی عملیاتی و امنیت:** Domain/API و کنترل دسترسی، بازیابی و اثرات جانبی آزموده شده‌اند.  
۲. **سلامت قرارداد مشترک:** ماژول از Core و Registry و Query/Action/Contribution معتبر استفاده می‌کند و برای هر ماژول جدید مجبور به بازنویسی گستردهٔ Host نیستیم.  
۳. **مشاهده و پذیرش مالک:** روی همان محیط روزمره، با دادهٔ نمایشی و حساب‌های واقعی نقش‌دار، قابل فهم و قابل آزمایش است.

این سه معیار مستقل‌اند و هر سه باید پیش از «پایان فاز» گزارش شوند. چهارمین قاعده: تغییر یک ماژول نباید بی‌دلیل کل هسته را بازنویسی کند.

## ۱۰. پروتکل بازگشت به این نقطه پس از چند پیام یا سشن جدید

در شروع تحلیل نتیجهٔ تحویل گزارش‌شدهٔ Codex:
1. این سند را بخوان و **نوع آن را Discussion/Proposed بدان**.
2. گزارش جدید Codex، SHA واقعی، تفاوت فایل‌ها و آزمایش‌های انجام‌شده را بررسی کن؛ وضعیت قبلی را به‌روز کن، نه اینکه بدون شاهد تکرار کنی.
3. قبل از دستور بعدی، سه سؤال بده: «چه چیزی واقعاً درست شد؟»، «چه چیزی هنوز با معماری محصول ناسازگار است؟»، «چه چیزی برای آزمون انسانی باقی است؟».
4. اجازه نده مرتب‌سازی ظاهری UI به جای تثبیت قراردادهای مشترک تمام شود؛ هم‌زمان بدون دلیل از UX به بازنویسی سراسری Backend نپر.
5. پیش از هر تغییر GitHub یا دستور Codex جدید، محدوده، ریسک و معیار پذیرش را خلاصه کن و تأیید صاحب محصول را بگیر.
6. برای سشن تازه فقط به حافظهٔ گفت‌وگو اتکا نکن: لینک/نسخهٔ همین سند، SHA کد و اسناد مرجع را در پیام شروع بده.

## ۱۱. آنچه اکنون نباید رخ دهد
