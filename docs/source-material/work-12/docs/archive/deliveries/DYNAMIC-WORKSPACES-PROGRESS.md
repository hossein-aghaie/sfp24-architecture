## Architecture and limits

The shared registry is `src/company/workspaces.ts`; policy resolution requires implemented/enabled modules, effective action permissions and administrator page/workspace restrictions. User preferences can only narrow/reorder reachable destinations. They cannot grant a module, action or resource. Job titles are not authorization. The company/user composite key and foreign key keep settings in their company. Add a workspace definition using existing pages to add another layout/navigation grouping; a genuinely new page also needs its actual renderer and server domain checks. There is no plugin system, generic dashboard builder or parallel backend.

Control migration5 adds `company_user_workspaces` with independent policy/preferences version counters; tenant schema remains5. Runtime receives only table DML, no DDL. Admin policy changes require current-password proof, optimistic version checking and audit. The users page must remain reachable for an effective company account manager. Existing password/session/capacity safeguards remain authoritative.

Monitoring readiness now refers to the implemented tenant scene and manual stored reporting display, not Edge, live equipment state, OEE, downtime or maintenance operations. OEE remains unknown without valid denominators. The future task registry may host other authorized operational forms; maintenance/quality task workflows, assignment engines and external integrations have not been built in this slice. Reports analytics remain a separate license. No owner password or existing user's permissions were reset for QA.

Evidence is ignored under `.local/qa/workspaces`, `.local/qa/unified-shell`, and `.local/qa/phase3b/pilot-regression`. `scripts/workspaces-qa.mjs` and `scripts/tenant-shell-qa.mjs` require explicit disposable fixture opt-in; they must not use real customer credentials or arbitrary production URLs. Authentication stays in memory; refreshing the browser requires sign-in again, while preferences remain in MariaDB.
