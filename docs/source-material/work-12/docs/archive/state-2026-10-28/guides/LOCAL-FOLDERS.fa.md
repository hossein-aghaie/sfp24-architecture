# پوشه‌های محلی و مصرف دیسک — ۲۰۲۶-۱۰-۱۹

## فایل‌های دائمی شرکت — ساختار اجرایی ۲۰۲۶-۱۰-۲۵

ریشهٔ فایل‌های جدید `D:/git/pouyeshgar-workshop/.local/companies` است؛ QA، کش یا public نیست. روی سرور، `companyFilesDirectory` در runtime config یا `COMPANY_FILES_ROOT` فقط ریشه را عوض می‌کند. مسیرها با شناسهٔ شرکت و دیوایس ساخته می‌شوند، نه نام قابل ویرایش آن‌ها:

```text
<company-files-root>/
  <company-uuid>/
    telemetry/sources/<source-or-draft-uuid>/
      draft.enc
      images/<sha256>.png|jpeg|webp
    library/models/
      <model-uuid>.glb
      <model-uuid>.json
```

عکس با بایت‌های اصلی و شفافیت PNG حفظ می‌شود؛ پیش‌نویس فقط مرجع تصویر را دارد. `draft.enc` سند JSON با AES-256-GCM و AAD شرکت/پیش‌نویس است. محدودیت کوتاه encryptToken دیگر روی سند اعمال نمی‌شود؛ محدودیت امنیتی خود توکن دست‌نخورده است. تصویر تا۱۵۰KiB و۲۰۴۸×۲۰۴۸ پذیرفته می‌شود. خواندن آن فقط با نشست و مجوز مدیریت هاب همان شرکت است؛ پوشه را static/public نکنید. حذف/تعویض عکس، باینری قبلی را خودکار پاک نمی‌کند؛ این فایل‌ها کش نیستند و پاک‌سازی به سیاست نگه‌داری جدا نیاز دارد.

کتابخانهٔ جدید نیز در همین ریشه نوشته می‌شود. مدل‌های قدیمی `.local/company-models/<SHA256-company-id>` و پیش‌نویس‌های قبلی `vaultDirectory/telemetry-wizards/<company-id>` با fallback خوانده می‌شوند؛ محیط یا فایل قبلی خودکار جابه‌جا نشده است. ذخیرهٔ بعدی پیش‌نویس، نسخهٔ تازه را در ساختار جدید می‌نویسد. تا انتقال کنترل‌شدهٔ فایل‌های قدیمی، آن دو مسیر را هم در backup نگه دارید.

کپی این پوشه فقط فایل‌های غیردیتابیسی را منتقل می‌کند. دیتابیس حساب‌ها/شرکت، vault رمز اتصال و کلید رمزگذاری برای بازیابی لازم‌اند. رمز ورود کاربران همچنان hash نمک‌دار در DB است؛ فایل رمز ورود داخل پوشهٔ شرکت ساخته نمی‌شود. vault و کلیدها مسیر خصوصیِ مستقل در تنظیمات دارند و با تغییر root شرکت جابه‌جا نمی‌شوند. dump/backup زمان‌بندی‌شده در این تغییر ساخته نشده است. بخش‌های تاریخ‌دار پایین سابقه‌اند؛ برای محل نوشتن فایل جدید، این بخش ملاک است.


محصول جاری در `D:/git/pouyeshgar-workshop` است. اندازه‌های زیر جمع اندازهٔ منطقی فایل‌ها بدون دنبال‌کردن junctionها هستند؛ اندازهٔ واقعی دیسک با hardlinkهای pnpm و فایل‌های فعال ممکن است فرق کند.

## نقشهٔ نگه‌داری داده برای انتقال به سرور — ۲۰۲۶-۱۰-۲۳

این بخش وضعیت کد فعلی را ثبت می‌کند؛ اندازه‌ها و گزارش پاک‌سازی بالا تاریخی‌اند. مالک ساخت پوشهٔ ظاهری و خالی را الزام نکرده است: محل واقعی داده، وابستگی‌ها و کار باقی‌مانده باید روشن باشند. همهٔ اطلاعات یک شرکت الزاماً داخل یک پوشه نیستند.

| چه چیزی | محل واقعی فعلی / روش نگه‌داری |
|---|---|
| نام کاربری و رمز ورود کاربران شرکت/مالک، مجوزها و خرید ماژول | دیتابیس مرکزی حساب‌ها؛ `company_users`/`platform_users` و جداول هویت. رمز ورود به‌صورت hash نمک‌دار scrypt است؛ فایل رمز قابل بازیابی برای کاربران ساخته نمی‌شود. |
| تنظیمات کاری شرکت، سالن، تجهیز، چیدمان و گزارش‌ها | دیتابیس مستقل همان شرکت؛ ارتباط company ID با نام دیتابیس و مرجع رمز اتصال در `tenant_storage` دیتابیس مرکزی است. |
| فایل GLB و مشخصات کتابخانه | `.local/company-models/<SHA256-company-id>/`؛ فایل `.glb` به همراه مشخصات `.json`. پوشه هنگام اولین ذخیره ساخته می‌شود، ورود به API از نشست شرکت کنترل می‌شود. این دادهٔ واقعی است، نه کش. |
| تنظیم اتصال API و worker | `.local/local-launcher/private/runtime.json` و `provision.json` در راه‌انداز محلی. اولی مجوز اتصال runtime دارد؛ دومی مجوز مدیریتی provisioning دارد و نباید به API/مرورگر داده شود. این‌ها فایل خصوصی‌اند و ممکن است رمز اتصال خواندنی داشته باشند. |
| رمز اتصال دیتابیس شرکت‌ها | پوشه‌ای که `vaultDirectory` در تنظیمات مشخص می‌کند؛ در محیط جاری زیر `.local/data-sources/private/vault-…/`. فایل‌ها با secret reference داخلی نام‌گذاری می‌شوند. اکنون JSON خصوصی و قابل خواندن برای سرورند، نه hash و نه vault رمزگذاری‌شدهٔ خارجی؛ سرور برای اتصال، خودِ رمز را لازم دارد. |

| فایل زندهٔ MariaDB | `.local/phase3/data/` طبق `mariadb-test.ini`، تحت مدیریت خود MariaDB؛ پوشهٔ دیتابیس را دستی داخل پوشهٔ شرکت جابه‌جا نکنید. |

### هنگام انتقال چه چیزهایی باید با هم منتقل شوند؟

دیتابیس مرکزی حساب‌ها، دیتابیس‌های شرکت‌ها، فایل‌های کتابخانه، vault و کلید رمزگذاری اجزای وابسته‌اند. کپی پوشهٔ سورس یا JSON چیدمان به‌تنهایی شرکت را بازسازی نمی‌کند. روی سرور جدید باید MariaDB آماده و داده از روش backup/restore معتبر منتقل شود؛ پوشهٔ فایل‌ها و کلیدها نیز با دسترسی محدود منتقل و مسیرهای تنظیمات اصلاح شوند. کپی سادهٔ datadir در زمان روشن‌بودن MariaDB روش انتقال این برنامه نیست. نمونه‌های آزمون و دمو جزء دادهٔ لازم محصول نیستند.

جهت استقرار نهایی: فایل‌های قابل نگه‌داری مستقل از پوشهٔ نسخهٔ کد باشند؛ ریشهٔ داده و مسیرهای کلید/vault از تنظیمات استقرار بیایند. مدل هر شرکت با شناسهٔ داخلی ثابت جدا بماند و نام یا کد ورود شرکت مسیر فایل را نسازد. پوشهٔ backup هر شرکت در آینده می‌تواند شامل dump و فایل‌ها به همراه manifest نسخه/شناسه باشد؛ دیتابیس مرکزی و کلیدها backup جدا و محدود می‌خواهند. اعتبارهای provisioning باید از اعتبارهای API جدا بمانند؛ مجوز Windows ACL یا Unix service user بخشی از تنظیم استقرار است و mode فایل به‌تنهایی روی Windows تضمین ACL نیست.

**کار باقی‌ماندهٔ مشخص:** ریشهٔ واحد دادهٔ قابل تنظیم برای همهٔ ورودی‌های runtime، اتصال مسیر کتابخانه به آن (اکنون مسیر پیش‌فرضش نسبت به cwd است)، یکپارچه‌سازی تنظیم کلید در entry point اصلی و محلی، ابزار backup/restore هماهنگ با DB و فایل و آزمون بازیابی، و جمع‌کردن فایل‌های شرکت در حذف نهایی. این موارد با ثبت این راهنما انجام‌شده محسوب نمی‌شوند. اکنون داده/کلید/سرویس زنده جابه‌جا یا بازسازی نشد و برای نمایش ساختار، پوشهٔ پسورد یا backup خالی ساخته نشد.

## چه چیزی پاک شد و چه چیزی باقی ماند؟

سه worktree قدیمی، کش‌های تکراری و برنچ‌های تأییدشده قبلاً پاک شدند. در بررسی تکمیلی، ZIP دانلودشدهٔ MariaDB پس از تطبیق SHA256 با فهرست ثبت‌شده و تأیید وجود runtime نصب‌شده حذف شد: ۹۴٬۹۷۰٬۰۴۹ بایت، حدود۹۱ MiB. این فایل برای اجرای عادی لازم نبود؛ نصب مجدد runtime به دانلود دوباره نیاز خواهد داشت. فایل فهرست checksum باقی است.

هیچ فایل دیتابیس، کلید، حساب یا دادهٔ ذخیره‌شده حذف نشد. تعداد زیادی schema با نام آزمایشی در datadir دیده می‌شود، اما نام پوشه به‌تنهایی اثبات بلااستفاده‌بودن نیست. پاک‌سازی آن‌ها باید با شناسایی control DB فعال و tenantهای وابسته، تهیهٔ پشتیبان لازم و دستور SQL انجام شود؛ حذف مستقیم پوشهٔ schema روش صحیح پاک‌سازی MariaDB نیست. این بررسی تکمیلی چنین تغییر دیتابیسی انجام نداد.

store و node_modules ممکن است از hardlink استفاده کنند؛ جمع دو اندازه الزاماً فضای فیزیکی جداگانه نیست. حذف store لزوماً برنامهٔ نصب‌شده را سبک‌تر نمی‌کند و نصب مجدد را به شبکه وابسته می‌کند. اکنون نگه داشته شد تا دمو و توسعه آماده بمانند.

## اجرای سه محیط

- فاز۲: `D:/git/pouyeshgar-demo-phase2/server-control/Start.cmd`؛ WEB5240 و API5184. دادهٔ ساختگی در JSON محلی است؛ دریافت واقعی یا MariaDB ندارد. هنگام این بررسی هر دو endpoint پاسخ دادند؛ اجرای کاربر متوقف نشد.
- هاب مستقل: `D:/git/pouyeshgar-industrial-platform/Start.cmd`؛ نسخهٔ نمایشی قدیمی با SQLite و تنظیمات خصوصی خودش. افزودن منبع واقعی آن را از حالت صرفاً نمایشی خارج می‌کند؛ در این مرحله منبع واقعی تنظیم نشد.
- محصول: `Check-Setup.cmd` بررسی پیش‌نیاز، `Start-All.cmd` اجرای صریح، `Status-All.cmd` وضعیت و `Stop-All.cmd` توقف فرایندهای متعلق به همین launcher. بررسی Check موفق بود؛ Start/Stop صرفاً برای آزمودن پاک‌سازی اجرا نشدند. هنگام بررسی محیط محصول و MariaDB خاموش بودند.

وابستگی‌های فاز۲ نصب شده‌اند و junctionهای vite/tsx به `.pnpm` خود آن دمو اشاره می‌کنند. store نصب در `../pouyeshgar-workshop/.local/pnpm-store` مشترک است. این چیدمان برای همین کامپیوتر است؛ ساخت installer یا بستهٔ ارائهٔ قابل‌حمل مرحله‌ای جداست.
