# روش ۴، سناریوی میهن — برای کاربر و آزمون مشترک

این سناریو رفتار هدف است، نه شرح قابلیت تکمیل‌شده. داده‌ها کاملاً مصنوعی‌اند.

## روز اول: شرکت و کار دستی

تو در Dev Admin شرکت آزمایشی میهن را با ماژول تولید و گزارش می‌سازی. WEB شرکت/قرارداد و مدیر اول را در control DB ثبت می‌کند. provisioning worker هسته دیتابیس مستقل میهن و جدول‌های عملیاتی و telemetry را آماده می‌کند. INGEST نه شرکت دیگری می‌سازد نه رمز مدیر را کپی می‌کند.

مدیر میهن در همان پنل یک تراش و۱۶دریل می‌سازد. WEB در جدول resources دیتابیس میهن می‌نویسد. این مرحله هیچ EdgeBox لازم ندارد. اپراتورها می‌توانند گزارش دستی بدهند.

## روز دوم: اتصال تراش

مدیر مجاز «منابع و تگ‌ها ← افزودن منبع» را می‌زند؛ نوع HTTPS، عنوان «ادج‌باکس تراش». WEB شرکت را از نشست خودش می‌گیرد، source UUID و credential می‌سازد؛ hash+route در control، source/config در دیتابیس میهن. وضعیت ایجاد ناقص باید pending باشد؛ credential تنها بعد از آماده‌بودن source فعال شود و retry ساخت باعث منبع تکراری نشود.

در همان فرم کانال count با نوع integer، واحد pcs و «تعداد کل پردازش‌شده در هر دقیقه» تعریف می‌شود؛ WEB signal UUID/definition را در telemetry_signals/definitions ثبت می‌کند. INGEST revision جدید را می‌بیند. کلید/endpoint/کانال در برگه تنظیم اتصال به مسئول نصب داده می‌شود؛ کلید در تاریخچه یا URL/اسکرین‌شات ذخیره نمی‌شود.

مدیر در تنظیمات تراش، تعداد کل را به تگ count متصل می‌کند. WEB در telemetry_input_bindings می‌نویسد. ضایعات، فرد و OP هنوز دستی‌اند. هیچ source→machine اجباری نداریم.

## ساعت ۹:۳۱: دریافت نمونه

عامل نمونهٔ دقیقه۹:۳۰تا۹:۳۱ را می‌فرستد. INGEST credential/source/channel/definition را بررسی می‌کند؛ received_at را خودش می‌گذارد. raw/receipt/sample و change sequence را در یک تراکنش دیتابیس میهن ثبت می‌کند و سپس رسید می‌دهد. همان اطلاعات را به API داخلی WEB دوباره POST نمی‌کند.

WEB از TelemetryReadService در همان DB می‌خواند؛ فرم با اعلان تغییر به‌روز می‌شود. اپراتور بازه واقعی کار را تعیین کرده، پس عدد مربوط به همان بازه را می‌بیند. نبود یک دقیقه ناقص است، نه صفر. صرف رسیدن count زمان روشن‌شدن دستگاه یا اپراتور را تعیین نمی‌کند.

## ساعت ۱۲: پایان یک کار

فرض کن بازهٔ کامل آزمایش۱۲۳ پردازش‌شده دارد؛ اپراتور۳ضایعات و دلیل می‌نویسد. WEB سالم۱۲۰ را محاسبه و در سرور کنترل می‌کند. هنگام تأیید، report/evidence/claims در تراکنش تولید ثبت می‌شوند؛ raw sensor history در telemetry می‌ماند. قطعه و OP ادعای گزارش‌اند، نه چیزی که از count حدس زده شده باشد.

## یک ماه بعد: دوربین ضایعات

مدیر یک منبع دیگر با کانال wast تعریف می‌کند. قرارداد آن «تعداد قطعات مردود نهایی هر دقیقه» است، نه تعداد فریم یا عیب. type/unit/interval در هاب ثبت و تگ در combo ضایعات دیده می‌شود. مدیر از تاریخ مشخص آن را منبع ضایعات تراش می‌کند. WEB فقط binding جدید می‌نویسد؛ گزارش‌های ماه قبل دست نمی‌خورند.

از آن زمان total و scrap هرکدام از تگ خود می‌آیند. فرد/قطعه/OP همچنان دستی‌اند. ناقص‌بودن هر منبع در فرم روشن است؛ نهایی‌کردن عدد نامطمئن خودکار مجاز نیست. مجوز override با دلیل، مسیر جداست.

## ادج‌باکس ۱۶ ورودی

مدیر یک source با۱۶کانال count_01 تا count_16 می‌سازد؛ WEB امکان ساخت گروهی و export پروفایل دارد. عامل فقط۱credential دارد و۱۶خروجی مجاز. در جدول تخصیص گروهی، هر signal به processed_count یک دریل وصل می‌شود. دادهٔ هر signal با ID ثابت خودش در telemetry_samples ثبت می‌شود. یکسان‌بودن دقیقه باعث تعارض کانال‌های مختلف نمی‌شود.

همان signal در کارت ماشین، نمودار و جمع گزارش قابل خواندن است؛ خواندن چندباره مصرف تولید چندباره ایجاد نمی‌کند. count بدون binding هم دریافت می‌شود و در لیست «بدون تخصیص» می‌ماند.

## قطعی و ارتقا

اگر عامل اینترنت نداشته باشد، صف خودش نمونه/زمان/شناسه را نگه می‌دارد. پس از اتصال همان نمونه‌ها را می‌فرستد؛ INGEST تکراری را دوباره جمع نمی‌کند. مقدار متفاوت برای همان signal/minute تعارض است.

اگر INGEST خاموش باشد WEB، کاربران و گزارش دستی مستقل می‌مانند؛ متصل‌ها no-fresh-data/worker-offline نشان می‌دهند. اگر MariaDB قطع شود هر دو بخش مشکل دارند؛ ACK جعلی/صفر جعلی تولید نمی‌کنیم.

اگر کلید باطل/شرکت معلق شود اتصال بعدی و دریافت تازه رد می‌شود؛ پیام از شرکت دیگری به DB میهن راه ندارد. با تغییر binding، late sample به ماشین زمان وقوع خودش تعلق دارد.

برای ارتقا، ابتدا سازگاری schema/contract مشخص، بعد migration افزایشی، سپس worker جدید و تست؛ قطع دریافت به عامل retry می‌دهد. WEB و INGEST ناسازگار ساکت اجرا نمی‌شوند. شروع/توقف از launcher همان پروژه است؛ برنامه‌های دیگر دست‌نخورده‌اند.
