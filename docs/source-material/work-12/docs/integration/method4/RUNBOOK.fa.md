# راهنمای آزمایش روش۴؛ برنامهٔ وب و دریافت‌کنندهٔ جدا

این راهنما مربوط به branch آزمایشی `codex/integrated-telemetry-v1` است. برنامهٔ فعلی شما خودکار عوض نشده است. پوش‌کردن کد به معنی روشن‌بودن سرویس یا آماده‌شدن broker نیست.

## مسیر کار مدیر شرکت

۱. در برنامهٔ اصلی، شرکت و ماشین‌ها را طبق روال قبلی تعریف کنید. برای ثبت دستی، ساخت منبع اتصال الزامی نیست.

۲. در «منابع و اتصال‌های داده»، «افزودن منبع اتصال» را بزنید. مثلاً «EdgeBox تراش»؛ روش HTTPS/POST یا MQTT؛ برای تست «آزمایشی». یک کانال با کلید count و معنای «کل قطعات پردازش‌شده در هر دقیقه» بسازید. در این مرحله هنوز ماشینی به EdgeBox نسبت داده نمی‌شود.

۳. فایل خصوصی تنظیم اتصال را همان لحظه دانلود کنید. کلید قابل بازیابی از فهرست نیست؛ در صورت گم‌شدن، از تنظیمات منبع کلید تازه بسازید و فرستنده را دوباره تنظیم کنید. اگر پاسخ ساخت منبع گم شد، retry همان درخواست منبع دیگری نسازد؛ کلید قبلی ممکن است دیگر در دسترس نباشد.

۴. آدرس دریافت باید آدرس **INGEST** باشد. WEB فرم را نشان می‌دهد؛ به‌صرف اینکه مثلاً روی پورت۵۲۰۶ صفحه باز است، دستگاه نباید POST را به آن بفرستد. در build وب، `VITE_TELEMETRY_INGEST_URL` آدرس تأییدشدهٔ listener جدید را تعیین می‌کند؛ اگر تنظیم نشده، فایل endpoint را null و مسیر نسبی را جدا نشان می‌دهد. تا آماده‌شدن هاب، آدرس حدسی وارد نکنید.

۵. در تب «استفاده در ماشین‌ها»، ورودی «تعداد کل پردازش‌شده» را انتخاب کنید، مقابل تراش تگ count را انتخاب و زمان شروع استفاده را ذخیره کنید. ساعت این کنترل صریحاً **UTC** است؛ ساعت تهران باید تبدیل شود. تخصیص از آن لحظه معتبر است؛ دادهٔ پیش از آن به ماشین جدید منتقل نمی‌شود.

۶. وقتی worker و فرستندهٔ سازگار داده را ثبت کنند، تب «اطلاعات دریافتی» زمان وقوع/دریافت و وضعیت آن را نشان می‌دهد. تعریف منبع یا دانلود فایل، اتصال واقعی را اثبات نمی‌کند. نبود دقیقه با تولید صفر فرق دارد. مقدار هر ردیف برای همان دقیقه است.

۷. فرم اپراتور برای ماشین و بازهٔ کارِ انتخاب‌شده، تعداد را خودکار می‌خواند. تا وقتی ضایعات به منبع متصل نشده، اپراتور مقدار و دلیل ضایعات را دستی می‌نویسد. شمارش کامل۱۲۳ و ضایعات۳ یعنی۱۲۰ سالم؛ اگر دقیقه‌ای نرسیده یا تعارض دارد، ثبت نهایی متصل منتظر بررسی می‌ماند. پیش‌نویس/جایگزینی دستیِ دارای مجوز و دلیل مسیر جداست.

۸. ماه بعد، دوربین نصب شد: منبع تازه با کلید wast و معنای «قطعات مردود نهایی در هر دقیقه» بسازید و آن را به ورودی «ضایعات نهایی» همان تراش تخصیص دهید. نام wast به‌تنهایی معنای ضایعات نمی‌دهد؛ قرارداد نوع و معنا تعیین‌کننده است.

۹. برای EdgeBox شانزده‌کاناله، تعداد کانال۱۶ و پیشوند count انتخاب کنید. کانال‌های count_01 تا count_16 ساخته می‌شوند؛ در تب تخصیص، هر کانال را مقابل دریل مربوط انتخاب و یک‌جا ذخیره کنید. دستگاه‌های تولید مستقل‌اند و EdgeBox الزاماً متعلق به یک ماشین نیست.

۱۰. «درخواست از عامل دریافت» فقط وضعیت/مکث/ادامهٔ جمع‌آوری داده را درخواست می‌کند؛ فرمان روشن/خاموش دستگاه تولید نیست. queued یعنی درخواست ثبت شده؛ اعمال‌شدن فقط پس از نتیجهٔ عامل معلوم می‌شود.

## مسئول راه‌اندازی؛ چه چیزی را اجرا می‌کند؟

این branch از runtimeهای موجود برنامهٔ اصلی استفاده می‌کند: API حساب‌ها و عملیات با `pnpm accounts:api`، رابط توسعه با `pnpm dev`. تنظیمات خصوصی API از راهنمای اصلی RUNBOOK خوانده شود؛ رمزها/پورت‌های اختصاصی شما از این سند بازنویسی نمی‌شوند. `pnpm dev` فعلی پورت۵۱۷۴ دارد و صرفاً اجرای dev server است، نه دریافت‌کنندهٔ دستگاه.

INGEST از repo هاب و دستور launcher همان branch اجرا خواهد شد؛ این repo broker دیگری روشن نمی‌کند. تا تحویل launcher هاب، دستور ساختگی برای اجرای آن نداریم. برای تست دوطرفه، آدرس‌ها و credential مخصوص fixture باید بین دو سشن هماهنگ شوند؛ هیچ port قدیمی یا سرویس در حال اجرا جایگزین نشود.

DDL/grants فقط با ابزار offline برنامهٔ اصلی و روی محیط موردتأیید اعمال شوند. برای credential **جداگانهٔ worker**، بعد از provision شدن tenant و schema جدید، ابزار زیر آماده است؛ اکنون روی شرکت‌های شما اجرا نشده:

```powershell
pnpm exec tsx tools/telemetry/provision-worker.ts --config <private-provision-config> --company <company-uuid>
```

خروجی خصوصی زیر `.local/telemetry/private/<company-uuid>/` است: تنظیم اتصال کنترل worker و vault tenant مخصوص INGEST. این پوشه حاوی رمز SQL است، در گیت یا چت قرار نگیرد. worker نباید به vault برنامهٔ WEB وصل شود. ابزار محیط isolated و پوشهٔ خروجی تازه می‌خواهد و هیچ سرویس را start نمی‌کند.

## آزمون توسعهٔ مستقل از سرویس‌های فعلی

از ریشهٔ worktree جدید اجرا شود. فقط config تست ایزولهٔ تأییدشده قابل‌قبول است؛ تست نام دیتابیس تصادفی می‌سازد و به شرکت‌های فعلی دست نمی‌زند.

```powershell
node node_modules/vue-tsc/bin/vue-tsc.js --noEmit
node node_modules/tsx/dist/cli.mjs --test tests/telemetry-contract.test.ts
node node_modules/tsx/dist/cli.mjs tools/telemetry/export-storage.ts --check
node node_modules/vite/bin/vite.js build

$env:PHASE3_MARIADB_TEST='isolated-local'
$env:PHASE3_LOCAL_CONFIG=(Join-Path $PWD '.local/phase3/private/provision.json')
$env:TELEMETRY_BROWSER_QA='1'
node node_modules/tsx/dist/cli.mjs --test tests/platform.integration.test.ts
```

گارد تست، MariaDB loopback پورت۳۳۱۷ و datadir مخصوص `.local/phase3/data` را بررسی می‌کند؛ سرویس را نصب/خاموش/جابه‌جا نمی‌کند. fixtureهای DB و تصاویر QA محلی و ignored هستند. browser QA کامپوننت واقعی را با API و DB واقعی fixture بررسی می‌کند؛ جای تست کامل shell یا receiver هاب نیست.

فهرست قابلیت‌های تأییدشده و محدودیت‌ها در `IMPLEMENTATION-STATUS.fa.md` است. روشن‌کردن برنامهٔ مالک یا migration شرکت‌های موجود، مرحلهٔ جدا پس از بررسی نتیجه است.

## fixture آماده برای هماهنگی با سشن هاب

برای ساخت محیط ساختگی تازه، با همان config تست ایزوله و پس از نصب وابستگی‌های همین branch:

```powershell
./tools/telemetry/Create-Fixture.ps1 -BrowserQA
```

این ابزار تست واقعی را اجرا می‌کند، شرکت `telemetry-fixture` را در control DB تصادفیِ تست می‌سازد و مسیر خروجی را چاپ می‌کند؛ اپلیکیشن یا worker را به‌عنوان سرویس دائمی روشن نمی‌کند. گزینهٔ BrowserQA اختیاری و برای Chrome نصب‌شده روی همین لپ‌تاپ است. هیچ داده یا binding تولید Seed نمی‌شود: یک تراش،۱۶دریل، دو منبع HTTP برای count/wast و یک منبع MQTT با۱۶کانال ساخته می‌شوند تا اتصال واقعی بعداً آزمایش شود.

خروجی زیر `.local/telemetry/private/fixture-platform_test_<run-id>/`:

- `web-runtime-private.json` و `web-vault/`: فقط برای برنامهٔ WEB.
- `ingest-runtime-private.json` و `ingest-vault/`: فقط برای worker هاب؛ رمز SQL آن با WEB متفاوت است.
- `device-profiles-private.json`: کلیدهای دستگاه‌های کاملاً ساختگی و تعریف کانال‌ها برای simulator هاب؛ endpoint باید با listener واقعی او تنظیم شود.
- `fixture-info-private.json`: اطلاعات ورود شرکت آزمایشی و شناسه‌های ماشین‌ها، برای تست پنل اصلی؛ به worker داده نشود.

این فایل‌ها خصوصی و ignored هستند؛ محتوایشان را به گیت/چت نفرستید. سشن هاب فقط profile مخصوص INGEST، vault خودش و device profiles همین fixture را مصرف کند، نه config دارای admin یا vault برنامهٔ WEB. secret_ref یکسان است، credential یکسان نیست.

برای API مستقل WEB، `PLATFORM_RUNTIME_CONFIG` را به web-runtime-private.json همان fixture بدهید و `pnpm accounts:api` را از همین worktree اجرا کنید؛ entry فعلی پورت۵۱۸۵ دارد. قبل از اجرا آزادبودن پورت بررسی شود؛ سرویس موجود را متوقف نکنید. رابط `pnpm dev` روی۵۱۷۴ به آن proxy می‌کند. اگر این پورت‌ها در استفاده‌اند، تا انتخاب و تنظیم پورت‌های جدا سرویس را اجرا نکنید. راه‌اندازهای قدیمی Start-All برای این fixture جدید نوشته نشده‌اند. launcher نهاییِ دوفرایندی پس از مشخص‌شدن listener و دستور اجرای branch هاب تکمیل می‌شود.
