# قواعد ارتباط بخش‌های برنامه

«قرارداد» یعنی توافق روشن دربارهٔ ارتباط دو بخش: چه اطلاعاتی ردوبدل می‌شود، کدام بخش مسئول آن است، چه مجوزی لازم دارد و در حالت خطا چه اتفاقی می‌افتد. مثلاً OEE باید بداند مقدار پارامتر را با چه زمان و واحدی می‌گیرد؛ آموزش باید بداند شخص و حساب را چطور از هسته شناسایی می‌کند.

## قواعد مستندشدهٔ برنامهٔ فعلی

این اسناد رفتار نسخهٔ بررسی‌شده را توضیح می‌دهند؛ همگی API عمومی نصب ماژول نیستند. جزئیات اجرایی هر اتصال باید با همان نسخهٔ کد تطبیق داده شود.

| موضوع ارتباط | سند و محدودیت |
|---|---|
| شناسایی شرکت، شخص، حساب و محدودهٔ دسترسی | [هویت و دسترسی](../core/IDENTITY-AND-ACCESS.fa.md)؛ نسخهٔ مبنای بررسی در سند مشخص است |
| دریافت داده و استفاده از تگ و پارامتر | [داده و پارامتر](../core/DATA-AND-PARAMETERS.fa.md)؛ [مصرف موجود در تولید](../operations/guides/PRODUCTION-DATA-SOURCES.md) |
| ساختار مرجع پیام صنعتی | [قرارداد تله‌متری](TELEMETRY.fa.md)؛ متن امضاشده در مخزن کد است و همهٔ آن در دریافت فعلی اجرا نشده |
| افزودن فیلد و صفحه در کد فعلی | [گسترش تعاریف](../core/EXTENSIONS.fa.md)؛ این سازوکار SDK عمومی نیست |

## اتصال‌هایی که هنوز طراحی نهایی ندارند

| پیش‌نویس | چه مسئله‌ای را قرار است حل کند؟ |
|---|---|
| [تعریف و اتصال یک ماژول](MODULE-CONTRACT-DRAFT.md) | نسخه، وابستگی، دسترسی، نصب و ارتقای ماژول |
| [ورودی و خروجی دادهٔ ماژول‌ها](DATA-CONTRACT-DRAFT.md) | نوع، زمان، منشأ، معنای مقدار و نتیجهٔ محاسبه |
| [افزودن بخش به رابط کاربر](UI-CONTRIBUTIONS-DRAFT.md) | صفحه، فرم، ابزار، بخش پروفایل و نمایش در میز کار |

این سه سند پیشنهاد طراحی‌اند؛ نمی‌توان با اتکا به آن‌ها وجود یک API قابل فراخوانی را فرض کرد. پیش از اجرا باید نیاز مصرف‌کنندگان، سازگاری نسخه و آزمون مشخص شوند. اگر برای کار ماژول به جزئیات بیشتری نیاز دارید، [درخواست از هسته](../governance/CHANGE-WORKFLOW.md) ثبت کنید؛ قرارداد موازی در پوشهٔ خود نسازید.
