# راهنمای وابستگی و یکپارچگی ماژول‌ها

> **وضعیت: Proposed — راهنمای معماری پیشنهادی، نه قرارداد اجرایی یا SDK مصوب**
>
> **مالک موضوع:** Core / Architecture · **تاریخ:** ۲۰۲۶-۱۱-۰۷
>
> این راهنما اصول طراحی ارتباط ماژول‌ها را برای صاحب محصول، معماران، نویسندگان ماژول و ایجنت‌های توسعه توضیح می‌دهد. درج این راهنما به‌معنی پیاده‌سازی API، Event Bus، Task Engine، نصب مستقل ماژول یا تأیید تمام مثال‌های آن نیست. هر اتصال اجرایی باید قرارداد و وضعیت پیاده‌سازی خودش را داشته باشد.

## ۱. قاعدهٔ اصلی

**ماژول‌ها باید از نظر مالکیت داده، منطق دامنه و چرخهٔ عمر مستقل باشند؛ اما باید بتوانند از طریق قراردادهای روشن با یکدیگر اطلاعات مبادله کنند و در فرایندهای سازمانی مشترک شرکت کنند.**

استقلال ماژول به معنی بی‌خبری آن از بقیهٔ سازمان نیست. یکپارچگی هم به معنی ادغام دیتابیس‌ها، اشتراک بی‌قیدوشرط جداول یا وابستگی اجباری همهٔ ماژول‌ها به یکدیگر نیست.

برای هر رابطه باید جداگانه مشخص شود:

1. چه ماژولی مالک داده و تصمیم دامنه‌ای است؟
2. کدام ماژول مصرف‌کنندهٔ اطلاعات است؟
3. این رابطه پیش‌نیاز اجباری است یا یک اتصال اختیاری؟
4. اگر ماژول یا منبع داده در دسترس نبود، رفتار قابل قبول چیست؟
5. چه قرارداد، نسخه، مجوز و آزمونی این رابطه را کنترل می‌کند؟

## ۲. چهار نوع رابطه را با هم اشتباه نگیریم

### ۲.۱. وابستگی پلتفرمی (Platform Dependency)

ماژول برای اجرا به قابلیت‌های عمومی پلتفرم نیاز دارد؛ مانند هویت معتبر، Tenant، مجوز و Scope. این وابستگی با وابستگی به یک ماژول کسب‌وکاری فرق دارد.

ماژول نباید برای Person، Account، Tenant یا Permission مدل موازی بسازد. باید از مرجع مشترک هسته استفاده کند.

### ۲.۲. وابستگی اجباری ماژولی (Required Domain Dependency)

قابلیت مشخصی بدون سرویس یا دادهٔ معتبر ماژول دیگر اساساً قابل ارائه نیست. این وابستگی باید صریح، نسخه‌دار و محدود به همان قابلیت باشد.

مثال: اگر قابلیتی با عنوان «محاسبهٔ تحقق برنامهٔ تولید» عرضه می‌شود، به دادهٔ معتبر برنامه و تحقق نیاز دارد. اما این موضوع به‌تنهایی به معنی وابستگی اجباری کل ماژول ثبت تولید به Planning نیست.

**وابستگی را تا حد امکان به سطح Capability محدود کنید، نه اینکه بی‌دلیل کل ماژول را وابسته کنید.**

### ۲.۳. یکپارچه‌سازی اختیاری (Optional Integration)

ماژول بدون اتصال هم قابلیت اصلی خود را انجام می‌دهد؛ اما با دریافت اطلاعات ماژول دیگر، تصمیم بهتر، پیشنهاد دقیق‌تر یا اتوماسیون بیشتری ارائه می‌کند.

مثال: Maintenance بدون Planning هم می‌تواند موعد سرویس و دستورکار تعمیر را مدیریت کند؛ با دریافت پنجره‌های برنامهٔ تولید می‌تواند زمان اجرای تعمیر را بهتر پیشنهاد دهد.

در این حالت نبود ماژول مقابل نباید به خطای نصب، توقف قابلیت پایه یا دادهٔ ساختگی منجر شود. قابلیت یکپارچه‌سازی باید غیرفعال، محدود یا قابل انجام به روش دستی باشد و این وضعیت به کاربر روشن اعلام شود.

### ۲.۴. گردش‌کار چندماژولی (Cross-Module Workflow)

یک فرایند سازمانی برای تکمیل مراحل خود به همکاری دو یا چند ماژول نیاز دارد. این همکاری لزوماً به معنی وابستگی چرخهٔ عمر ماژول‌ها به یکدیگر نیست.

مثال: برنامه‌ریزی محصول جدید، برآورد ظرفیت تولید، شناسایی شکاف مهارتی، آموزش کارکنان و آماده‌سازی خط می‌تواند یک گردش‌کار مشترک باشد. هر ماژول همچنان مالک داده و تصمیم تخصصی خودش باقی می‌ماند.

برای هر گردش‌کار باید مالک فرایند، مراحل، مسئول تأیید، وضعیت‌های میانی، خطا، لغو، جبران و سابقهٔ ممیزی روشن باشد. وجود یک Task Engine یا Workflow Engine عمومی در Runtime فعلی را نباید از این نیاز نتیجه گرفت.

## ۳. ارتباط، وابستگی و مالکیت داده

سه مفهوم مستقل‌اند:

- **مالکیت (Ownership):** مسئول تعریف معنا، اعتبارسنجی، تغییر، نسخه و چرخهٔ عمر داده کیست؟
- **ارتباط (Integration):** چه اطلاعات یا درخواستی بین دو حوزه مبادله می‌شود؟
- **وابستگی (Dependency):** نبود طرف مقابل کدام قابلیت را از ارائه بازمی‌دارد؟

مصرف‌کننده می‌تواند به اطلاعات ماژول مالک نیاز عملیاتی داشته باشد، بدون آنکه مالک آن اطلاعات شود.

برای مثال:

| موضوع | مالک پیشنهادی | مصرف‌کنندهٔ احتمالی |
|---|---|---|
| برنامه و پیش‌بینی تولید | Planning | Maintenance، Training، MRP |
| گزارش واقعی تولید | Production | OEE، Planning، Training |
| موعد فنی سرویس و دستورکار تعمیر | Maintenance | Planning برای هماهنگی توقف |
| فعالیت و الزام شایستگی | Training، با ورودی معتبر حوزهٔ تخصصی | برنامه‌ریزی نیروی کار، مدیران مجاز |
| هویت Person و Account | Core | همهٔ ماژول‌های مجاز |

این جدول نمونهٔ مرزبندی دامنه است، نه اعلام وضعیت پیاده‌سازی یا قرارداد نهایی این ماژول‌ها.

**منبع رسمی داده را در ماژول مصرف‌کننده تکثیر نکنید.** مصرف‌کننده می‌تواند Snapshot یا سابقهٔ دریافت‌شدهٔ لازم را برای ردیابی، عملکرد یا ممیزی نگه دارد؛ اما باید منشأ، شناسه، نسخه و زمان منبع روشن باشد و آن Snapshot به‌اشتباه منبع رسمی و قابل ویرایش معرفی نشود.

## ۴. قواعد ارتباط فنی

### ۴.۱. دسترسی مستقیم به دیتابیس ماژول دیگر ممنوع به‌عنوان الگوی پیش‌فرض

یک ماژول نباید برای خواندن یا تغییر دادهٔ دامنهٔ ماژول دیگر مستقیماً به جداول داخلی آن متصل شود. نام جدول، ساختار Migration یا جزئیات ذخیره‌سازی، قرارداد عمومی نیستند.

مسیر مطلوب، قرارداد تایپ‌شده و نسخه‌دار است؛ مانند Service/Port، Query، Event یا Command. انتخاب مکانیزم نهایی باید با معماری اجرایی و نیاز واقعی سازگار شود.

### ۴.۲. تفاوت Query، Event و Command

| نوع | معنا | مثال |
|---|---|---|
| Query | درخواست خواندن اطلاعات معتبر در یک محدوده و زمان مشخص | «پنجره‌های توقف برنامه‌ریزی‌شدهٔ این خط چیست؟» |
| Event | اعلام یک واقعیت رخ‌داده؛ مصرف‌کننده خودش تصمیم می‌گیرد چه کند | «برنامهٔ تولید نسخهٔ جدیدی منتشر شد.» |
| Command | درخواست انجام یک عمل از مالک آن عمل | «این پنجرهٔ توقف را برای بررسی ثبت کن.» |

Event نباید بی‌اجازه به معنی Command یا تأیید تلقی شود. دریافت Event از یک ماژول به مصرف‌کننده اجازهٔ تغییر دادهٔ مالک را نمی‌دهد. Command باید مجوز، Scope، اعتبارسنجی، نتیجه و سابقهٔ قابل پیگیری داشته باشد.

### ۴.۳. قرارداد داده باید معنای آن را حفظ کند

حداقل مواردی که بسته به نوع داده باید مشخص شوند:

- شناسه و نسخهٔ قرارداد و منبع؛
- شناسهٔ موجودیت و محدودهٔ شرکت، سایت، تجهیز یا شخص؛
- معنای دقیق مقدار، نوع، واحد و روش محاسبه؛
- زمان مشاهده/وقوع، زمان ثبت و در صورت نیاز بازهٔ اعتبار؛
- وضعیت داده: واقعی، برنامه‌ریزی‌شده، پیش‌بینی، پیشنهادی، تأییدشده یا لغوشده؛
- کیفیت، تازگی، منشأ و محدودیت داده؛
- مجوز خواندن یا انجام عمل و Scope مربوط؛
- رفتار تعارض نسخه، دادهٔ تکراری، تأخیر و عدم دسترسی.

**نامعلوم مساوی صفر نیست؛ پیش‌بینی مساوی برنامهٔ تأییدشده نیست؛ پیشنهاد مساوی تصمیم نیست.**

### ۴.۴. ارتباط دوطرفه مجاز است؛ وابستگی چرخه‌ای اجباری نه

دو ماژول می‌توانند Query، Event یا Command دوطرفه داشته باشند. این موضوع به‌خودی‌خود ایراد معماری نیست.

اما گراف وابستگی‌های اجباری باید بدون چرخه طراحی شود. برای نمونه، Maintenance نباید برای فعال‌شدن به Planning وابسته باشد و Planning هم برای فعال‌شدن به Maintenance. حلقه‌های تبادل Event نیز باید با شناسهٔ هم‌بستگی، تشخیص پیام تکراری و قواعد جلوگیری از بازتولید بی‌پایان کنترل شوند.

## ۵. مثال اول: نگهداری و تعمیرات پیشگیرانه (Preventive Maintenance)

Maintenance باید حتی بدون نصب Planning یا Production بتواند سیاست سرویس، موعد فنی، سوابق، درخواست و دستورکار تعمیر را مدیریت کند.

### مالکیت اطلاعات

| اطلاعات یا تصمیم | مالک |
|---|---|
| سیاست فنی PM، تناوب سرویس و دستورکار | Maintenance |
| موعد فنی مبتنی بر تقویم، ساعت کارکرد، سیکل، وضعیت تجهیز یا الزام سازنده | Maintenance؛ با مصرف شواهد معتبر |
| برنامه و پیش‌بینی تولید | Planning |
| گزارش واقعی تولید و زمان‌های ثبت‌شدهٔ عملیات | Production |
| دادهٔ خام حسگر و تله‌متری | منبع/زیرساخت دریافت و قرارداد دادهٔ مربوط |
| پیشنهاد زمان اجرای تعمیر | Maintenance |
| پذیرش اثر توقف بر برنامه و تعهد تولید | Planning/Production طبق اختیار تعریف‌شده |

### گردش نمونه

1. Maintenance بر اساس قاعدهٔ فنی یا شواهد معتبر تشخیص می‌دهد سرویس در چه زمانی سررسید می‌شود.
2. Maintenance برای اجرای آن، پنجرهٔ توقف مناسب درخواست یا پیشنهاد می‌کند.
3. اگر اتصال Planning موجود و مجاز باشد، Maintenance برنامه و پنجره‌های احتمالی توقف را دریافت می‌کند.
4. Planning/Production اثر توقف را بررسی می‌کند و پنجره را می‌پذیرد، رد می‌کند یا زمان دیگری پیشنهاد می‌دهد.
5. Maintenance زمان اجرایی را ثبت و دستورکار را طبق فرایند خودش مدیریت می‌کند.

برنامهٔ تولید نباید موعد فنی PM را خودسرانه جابه‌جا یا حذف کند. ممکن است تعمیر از نظر فنی سررسید شده باشد، حتی اگر برنامهٔ تولید توقف مناسبی نشان ندهد. در چنین وضعی باید تعارض و ریسک به مسئول مجاز ارجاع شود، نه اینکه موعد فنی پنهانی تغییر کند.

اگر Planning/Production نصب نباشد یا دادهٔ آن‌ها در دسترس نباشد، Maintenance باید بتواند با برنامه‌ریزی دستی و اعلام محدودیت ادامه دهد.

## ۶. مثال دوم: آموزش و نیاز مهارتی شش ماه آینده

Training فقط ثبت دوره و مشاهدهٔ محتوای آموزشی نیست. می‌تواند شکاف مهارتی فعلی و نیاز احتمالی آینده را تحلیل کند؛ اما برای این کار باید از چند حوزه اطلاعات معتبر بگیرد.

| اطلاعات موردنیاز | مالک یا منبع معتبر احتمالی |
|---|---|
| Person و هویت سازمانی | Core و حوزهٔ مدیریت افراد |
| مهارت، شاهد، ارزیابی، صلاحیت و شکاف مهارتی | Training |
| محصول، نسخه و تغییرات محصول | Product/Engineering |
| فرآیند، عملیات و معیار تخصصی کار | Engineering و حوزهٔ عملیاتی مالک آن |
| حجم و سناریوهای تولید آینده | Planning |
| تجهیزات و خطوط درگیر | حوزهٔ مالک دارایی/تجهیز و دادهٔ معتبر آن |
| نیاز شیفت و ظرفیت نیروی انسانی | Planning یا Workforce Management |
| دوره، تخصیص، ارزیابی و برنامهٔ آموزش | Training |

### گردش نمونه

1. Planning پیش‌بینی یا سناریوی تولید محصول جدید را با بازهٔ زمانی و وضعیت اعتبار منتشر می‌کند.
2. حوزهٔ تخصصی مربوط، فعالیت‌ها و مهارت‌های لازم را با نسخه و Scope مشخص می‌کند.
3. Training الزامات را با شواهد و صلاحیت معتبر کارکنان مقایسه می‌کند.
4. Training شکاف فعلی و شکاف احتمالی آینده را جداگانه محاسبه می‌کند.
5. Training پیشنهاد می‌دهد چه افرادی، تا چه تاریخی و با چه مسیر آموزشی آماده شوند.
6. مسئولان مجاز، نیاز، بودجه، زمان و تخصیص را بررسی و تصویب می‌کنند.
7. آموزش، ارزیابی و تصمیم Qualification طبق چرخهٔ مستقل Training ثبت می‌شوند.

Training نباید از روی نام محصول یا Job Title مهارت لازم را حدس بزند. باید رابطهٔ محصول/فرآیند با Activity و Competency از منبع معتبر و نسخه‌دار بیاید.

پیش‌بینی شش‌ماهه نباید بدون تأیید انسانی به الزام قطعی آموزش تبدیل شود. وضعیت سناریو، احتمال/عدم‌قطعیت، تاریخ اعتبار و نسخهٔ برنامه باید همراه داده بماند. همچنین شیفت پایه به‌تنهایی اثبات حضور، آزادبودن شخص یا ظرفیت واقعی مربی نیست.

اگر Planning یا Production نصب نباشد، Training باید امکان تعریف دستی Activity، Requirement، هدف زمانی و برنامهٔ آموزش را حفظ کند؛ فقط تحلیل خودکار مبتنی بر برنامهٔ تولید در دسترس نخواهد بود.

## ۷. رفتار در نبود یا اختلال اتصال

برای هر اتصال، حداقل این وضعیت‌ها را طراحی و آزمون کنید:

| وضعیت | رفتار مورد انتظار |
|---|---|
| ماژول مقابل نصب نیست | قابلیت پایهٔ ماژول جاری ادامه یابد؛ قابلیت اختیاری غیرفعال یا دستی شود |
| ماژول نصب است ولی مجوز مصرف وجود ندارد | دسترسی رد شود؛ داده از مسیر جایگزین یا Cache غیرمجاز افشا نشود |
| سرویس یا منبع موقتاً در دسترس نیست | خطای قابل فهم، Retry کنترل‌شده یا آخرین Snapshot مجاز با نمایش زمان و کهنگی |
| داده قدیمی یا ناقص است | کیفیت/تازگی اعلام شود؛ تصمیم قطعی از دادهٔ نامعتبر ساخته نشود |
| نسخهٔ قرارداد ناسازگار است | اتصال رد یا به مسیر سازگار محدود شود؛ خطای پنهان و تفسیر حدسی ممنوع |
| برنامه تغییر کرده یا لغو شده است | نسخه و وضعیت جدید منتشر شود؛ مصرف‌کننده اثر را بررسی کند و تاریخچه را بازنویسی نکند |

Fallback دستی باید صریح باشد: چه کسی، چه داده‌ای، با چه منبعی و تا چه زمانی وارد می‌کند؟ دادهٔ دستی باید به‌عنوان دستی شناخته شود، نه اینکه وانمود کند از ماژول غایب آمده است.

## ۸. امنیت و مرز اعتماد

- Tenant از Actor معتبر سمت سرور به دست می‌آید؛ شناسهٔ شرکت ارسالی مرورگر به‌تنهایی قابل اعتماد نیست.
- Entitlement، Permission و Scope برای هر Query و Command در Backend کنترل می‌شوند.
- داشتن مجوز مشاهده، مجوز تغییر یا تأیید نیست.
- مجوز یک ماژول، مجوز دسترسی آزاد به همهٔ داده‌های ماژول دیگر ایجاد نمی‌کند.
- دادهٔ شخصی، محرمانه و صنعتی باید به حداقل لازم محدود شود.
- عملیات حساس، تغییر برنامه، تأیید توقف، صدور صلاحیت و تصمیم‌های مشابه باید Actor، زمان، دلیل و نسخهٔ مبنا داشته باشند.
- نمایش یا مخفی‌کردن UI جای کنترل مجوز سمت سرور را نمی‌گیرد.

## ۹. چک‌لیست نویسندهٔ ماژول

پیش از درخواست اتصال یا پیاده‌سازی، پاسخ این موارد را در سند ماژول یا درخواست از هسته ثبت کنید:

1. این قابلیت دقیقاً چه مسئله‌ای را حل می‌کند؟
2. مالک هر داده و تصمیم دامنه‌ای کدام بخش است؟
3. کدام داده واقعاً لازم است و کدام فقط کیفیت قابلیت را بهتر می‌کند؟
4. رابطه Required Dependency، Optional Integration یا Cross-Module Workflow است؟
5. اگر ماژول مقابل نصب، فعال یا در دسترس نبود چه اتفاقی می‌افتد؟
6. ورودی چه معنا، نوع، واحد، نسخه، زمان، Scope، منشأ و وضعیت اعتباری دارد؟
7. اتصال Query است، Event است یا Command؟ چه کسی اجازهٔ پاسخ یا تأیید دارد؟
8. رفتار دادهٔ قدیمی، تکراری، متعارض، ناقص و نسخهٔ ناسازگار چیست؟
9. Tenant، Entitlement، Permission، Scope و Audit چگونه کنترل می‌شوند؟
10. آیا می‌توان قابلیت پایه را بدون ماژول مقابل اجرا و آزمون کرد؟
11. آیا تغییر داخلی ماژول مقابل، بدون تغییر قرارداد عمومی، مصرف‌کننده را می‌شکند؟
12. آزمون نصب‌بودن، نصب‌نبودن، قطع اتصال، مجوز ناکافی، دو Tenant و نسخهٔ ناسازگار کجاست؟

## ۱۰. دستورالعمل ایجنت‌های توسعه

ایجنت یا توسعه‌دهنده باید:

- پیش از پیشنهاد تغییر، README ماژول، اسناد هسته، قراردادها و وضعیت واقعی پیاده‌سازی را بخواند.
- برای هر اتصال، مالک داده، مصرف‌کننده و نوع رابطه را صریح اعلام کند.
- بین Observed، Proposed، Approved و Implemented تمایز بگذارد.
- از روی این راهنما Endpoint، جدول، Event Bus، SDK یا Task Engine موجود فرض نکند.
- مستقیم به دیتابیس ماژول دیگر متصل نشود و مدل دامنهٔ تکراری نسازد.
- وابستگی اجباری را بدون سناریوی اثبات‌شده و تأیید لازم اضافه نکند.
- نبود ماژول اختیاری را در طراحی و آزمون پوشش دهد.
- تغییر مشترک Core یا قرارداد را جداگانه توضیح دهد؛ تأیید یک نیاز ماژول مجوز تغییرات دیگر نیست.
- شواهد آزمون و محدودیت‌های اثبات‌نشده را گزارش کند.

## ۱۱. وضعیت این راهنما و مسیر تبدیل به قرارداد اجرایی

این راهنما اصول و مثال‌های طراحی را یک‌جا می‌کند؛ اما نام عملیات، Schema، Endpoint، Permission، Event، سازگاری نسخه و روش نصب را نهایی نمی‌کند.

در معماری بررسی‌شده، ساختار برنامه عمدتاً Modular Monolith است. Registryها و Serviceهای داخلی وجود دارند، اما **Module SDK عمومی، نصب و توزیع مستقل، Event Bus عمومی و Task/Workflow Engine مشترک را نباید قابلیت آمادهٔ Runtime فرض کرد.**

برای تبدیل یک اتصال به قابلیت اجرایی:

1. سناریوی واقعی و نیاز مصرف‌کننده ثبت شود.
2. مالکیت داده و نوع رابطه تعیین شود.
3. درخواست مشترک طبق [گردش تغییر](../governance/CHANGE-WORKFLOW.md) ثبت و به Core/مالک دامنه ارجاع شود.
4. قرارداد مشخص و نسخه‌دار، شامل خطا و مجوز، بررسی و تأیید شود.
5. پیاده‌سازی با نسخهٔ واقعی Core تطبیق داده شود.
6. آزمون مستقل و یکپارچه، شامل نبود ماژول و مرز Tenant، انجام شود.
7. وضعیت واقعی و شواهد در سند مالک و گزارش تحویل ثبت شوند.

**تا پیش از تأیید قرارداد و اثبات کد، این راهنما مبنای تحلیل و طراحی است، نه مجوز ادعای وجود قابلیت یا شروع خودکار پیاده‌سازی.**
