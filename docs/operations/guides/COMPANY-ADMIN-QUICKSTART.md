# مدیریت سادهٔ شرکت و کاربران / Company administration

> نسخهٔ راهنمای موضوعی؛ کد مبنا b3f203b، بازبینی انتقال ۲۰۲۶-۱۱-۰۲. متن اولیه در [کاتالوگ منابع](../../sources/CATALOG.md) محفوظ است. دستورها برای مخزن محصول و محیط مشخص همان نسخه‌اند؛ خود مخزن اسناد اجرا نمی‌شود.


این راهنما برای نسخهٔ ساده‌شدهٔ Phase 3A است. ایمیل اجباری نیست؛ رمز فعلی کاربران هرگز به مدیر نشان داده نمی‌شود.

## استفادهٔ روزمره

ادمین شرکت از **مدیریت سامانهٔ شرکت ← امکانات و ظرفیت شرکت**، ماژول‌های فعال و ظرفیت کل/حساب‌های فعال/جای خالی را می‌بیند. این صفحه فقط نمایشی است؛ تغییر خرید و ظرفیت با ادمین نرم‌افزار است. ظرفیت شامل مدیر و همهٔ حساب‌های فعال است، نه تعداد کاربران هم‌زمان. اگر سیاست فضای کاری کاربر صریحاً محدود شده، صفحهٔ جدید باید در همان سیاست مجاز شود. در ساخت شرکت جدید، «ثبت و گزارش تولید» پیش‌فرض انتخاب شده است؛ ادمین نرم‌افزار می‌تواند آن را با مشاهدهٔ هشدار بردارد.

1. صاحب نرم‌افزار از `http://127.0.0.1:5176/owner/login` وارد می‌شود. ورود کاربران شرکت‌ها صفحهٔ جداگانهٔ `http://127.0.0.1:5176/company/login` دارد؛ روی صفحهٔ شرکت انتخاب ورود صاحب نرم‌افزار وجود ندارد. اطلاعات ورود خصوصی است و در Git نگه‌داری نمی‌شود.
2. **افزودن شرکت**: نام، ظرفیت کاربران با احتساب مدیر، و ماژول‌ها را تعیین کنید. کد شرکت خودکار ساخته می‌شود؛ تنظیم دستی کد و نام کاربری مدیر اولیه اختیاری است.
3. آماده‌سازی دیتابیس خودکار است، مشروط به روشن‌بودن پردازشگر محلی. وضعیت شرکت باید به **آمادهٔ ورود مدیر** برسد. برگهٔ ورود مدیر فقط همان بار نمایش داده می‌شود؛ آن را خصوصی کپی/دریافت و به خود مدیر تحویل دهید.
4. دریافت‌کننده لینک برگه را باز می‌کند و رمز شخصی می‌سازد. همچنین می‌تواند کد موقت را در کادر رمز ورود وارد کند تا مستقیماً به تعیین رمز هدایت شود. سپس با کد شرکت، نام کاربری و رمز شخصی وارد می‌شود.
5. **ویرایش شرکت** برای تغییر نام، ظرفیت و امکانات است. ظرفیت کمتر از کاربران فعال پذیرفته نمی‌شود. انتخاب ماژول ناتمام، آن را عملیاتی نمی‌کند.
6. مدیر شرکت از **افزودن کاربر** و **ویرایش کاربر** برای نام کاربری، نقش آماده و فعال/غیرفعال‌کردن استفاده می‌کند. کاربران غیرفعال ظرفیت فعال را مصرف نمی‌کنند؛ فعال‌سازی مجدد سقف ظرفیت را رعایت می‌کند. آخرین مدیر فعال قابل حذف نقش/غیرفعال‌کردن نیست.
7. صاحب نرم‌افزار از **کاربران و پشتیبانی**، با تأیید رمز خودش، علت و کد شرکت، برای ۱۰ دقیقه به مدیریت کاربران همان شرکت دسترسی می‌گیرد. این اجازه، دسترسی به دادهٔ تولید نیست.
8. **بازنشانی رمز** یک برگهٔ جدید می‌دهد؛ نشست‌های قبلی فوراً باطل می‌شوند. برای مدیر شرکت و مدیر اولیه، رمز خود مدیر اقدام‌کننده و تأیید کد شرکت نیز لازم است. **تغییر رمز من** به رمز فعلی نیاز دارد و همهٔ نشست‌های قبلی را می‌بندد.
9. صاحب نرم‌افزار در فهرست شرکت‌ها می‌تواند **غیرفعال‌کردن شرکت** را بزند و رمز خودش را تأیید کند. ورود، نشست‌ها، فعال‌سازی کاربران و دسترسی شرکت بسته می‌شوند؛ دیتابیس، کاربران، ظرفیت و ماژول‌ها حذف نمی‌شوند. **فعال‌سازی مجدد** شرکت را به مرحلهٔ قبلی برمی‌گرداند؛ نشست‌های قدیمی برنمی‌گردند و ورود دوباره لازم است. حذف دائمی شرکت هنوز پیاده نشده است؛ شرکت‌های تستی فعلاً باقی می‌مانند.
10. کنار هر شرکت **کپی لینک ورود** قرار دارد؛ لینک اختصاصی به شکل `/company/<company-code>/login` است و کد شرکت را خودکار مشخص می‌کند. همان لینک را به مدیر و کاربران آن شرکت بدهید. برگه‌های فعال‌سازی جدید هم در همین مسیر شرکت باز می‌شوند. آدرس قدیمی `/?accounts=1` به ورود صاحب نرم‌افزار هدایت می‌شود؛ برگه‌های قدیمی دارای کد فعال‌سازی به مسیر شرکت هدایت می‌شوند و همچنان کار می‌کنند.

برگهٔ فعال‌سازی ۲۴ ساعت و برگهٔ بازنشانی کاربر دارای رمز ۳۰ دقیقه اعتبار دارد. هر برگه یک‌بارمصرف است. اگر منقضی/گم شد، برگهٔ جدید صادر کنید؛ رمز قبلی قابل بازیابی یا مشاهده نیست. پس از ویرایش کاربرِ منتظر تعیین رمز، برگهٔ جدید لازم است. حساب فعالِ در انتظار بازنشانی همچنان جزو ظرفیت است.

نقش‌ها قالب‌های آماده‌اند، نه مجوز دلخواه برای هر عملیات. ماژول باید هم در قرارداد فعال، هم واقعاً پیاده‌شده و هم در مجوز نقش باشد. داده‌ها و ماژول‌های عملیاتی Phase 2 هنوز از این حساب‌ها مستقل‌اند. ورود دومرحله‌ای، بازیابی خودکار حساب صاحب نرم‌افزار و صفحهٔ مشاهدهٔ Audit هنوز ساخته نشده‌اند؛ رویدادهای حساس در دیتابیس ثبت می‌شوند.

## Developer and operator notes

- Additive control migration **2** adds credential/session versions, forced personal-password state, invitation purpose, bounded support grants and provisioning queue/heartbeat. Migration 1 and tenant migrations remain unchanged. Back up the approved control database privately before applying an upgrade; use the existing migration command and repeat it to verify replay.
- Control migration **3** adds an independent `company_accounts.suspended` flag, preserving provisioning/onboarding status. `PATCH /api/v1/provider/companies/:id/suspension` requires a provider session, `{suspended: boolean, currentPassword}` and password reauthentication; it locks the company, revokes company sessions/support grants and audits suspend/resume atomically. HTTP runtime gains DELETE only on support grants for revocation. Login rechecks suspension under the company lock, activation and tenant storage fail closed, and no database or user is deleted. Suspension is company-wide in account mode; the independent Phase 2 pilot is not tenant-scoped and is unaffected.
- Run `pnpm accounts:worker` in a **separate restricted local terminal/process** with `PLATFORM_PROVISION_CONFIG` pointing to the approved private provisioner config. The HTTP process uses only `PLATFORM_RUNTIME_CONFIG`; never pass the elevated config to it. The worker invokes the existing resumable provisioner, claims jobs with a database advisory lock, and does no automatic DROP or destructive compensation. The UI is truthful when the worker is offline; preparation can resume from the panel.
- The already-approved laptop uses ignored `.local/phase3/Start-Test.cmd` and `Stop-Test.cmd` for its own web/API/worker/MariaDB processes only (loopback web 5176, API 5186, DB 3317). This is local test setup, not a production service installation.
- Passwords use the existing salted scrypt KDF. Temporary codes and sessions are stored as hashes; codes travel in a URL fragment removed immediately after loading. They are not placed in query strings, persistent browser storage, audit records or screenshots. Deliver sign-in cards privately; downloading a card creates a confidential file under the operator's control.
- `CredentialsService` owns password change, reset completion and support authorization. `managedCompany` scopes company-user actions. It never grants production-data access. Original-admin recovery remains privileged even after a role change. Role changes and disables revoke sessions; session credential versions prevent stale-login races after password changes.
- New versioned endpoints: `POST /api/v1/password/change`; `POST /api/v1/provider/companies/:id/support`; provider-scoped `GET/POST .../:id/users`, `PATCH .../:id/users/:userId`, `POST .../:id/users/:userId/reset`; `POST /api/v1/company/users/:id/reset`; `GET /api/v1/provider/provisioning`; `POST /api/v1/provider/companies/:id/provisioning/retry`. Activation and invitations retain their original endpoint contracts.
- `pnpm test` skips the database suite unless explicitly opted in. Disposable CI uses `PHASE3_MARIADB_TEST=isolated-ci`. The approved laptop test uses `isolated-local` plus `PHASE3_LOCAL_CONFIG` equal to the absolute `.local/phase3/private/provision.json`; its guard checks loopback, port and isolated data directory before creating random fixture databases. No existing owner company is used as a test fixture.
- Connected browser QA: set `PHASE3_UI_QA_CREATE_FIXTURE=1`, `PHASE3_QA_LOGIN_FILE` to a private provider login JSON, optionally `PHASE3_QA_URL` (loopback only), then run `node scripts/phase3-admin-qa.mjs`. **Each run creates an explicitly fictional QA company** with a real separate tenant DB. It never edits pre-existing companies. Artifacts are ignored under `.local/qa/phase3-usability`; confidential card/password fields are masked. Provisioning worker and API must be running. The older `phase3-ui-qa.mjs` documents the previous UI/fixture baseline and is superseded for current panel acceptance.
- When the owner has changed their personal password, do not reset it or reuse the stale bootstrap file for automation. Browser QA also accepts `PHASE3_QA_API_URL` pointing to a separately approved disposable loopback Fastify API backed by real isolated MariaDB fixtures and its own test-provider login file. The browser uses a transparent test transport proxy; response data are real API/DB results, not mocks. This does not change the normal laptop API or any existing owner account.
- `src/accounts/routes.ts` owns the small login-route contract; the entry path fixes the client account kind, with no role-selector tabs. This is a usability boundary only: existing server authentication/RBAC remains authoritative. No separate domain, server deployment or authentication implementation was introduced. Static production hosting will need the usual SPA fallback for these paths; no production hosting was configured or validated here.

Production TLS, managed secret storage, OS/service isolation, disaster recovery, load testing and independent security review remain separate work; this local workflow is not a production-hardening claim.
